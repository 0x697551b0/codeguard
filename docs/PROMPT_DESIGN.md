# Prompt 设计说明

Prompt 是 Agent 的"行为规范"。CodeGuard 的 Prompt 分为三层，各有明确职责。

```
┌─────────────────────────────────────────────────────────────┐
│ ① System Prompt（prompts.system_prompt）                     │
│    角色 / 工作流程 / 审查纪律 / 工具规范 / 输出语言            │
│    —— 决定 Agent 的整体行为边界，整个会话固定不变              │
├─────────────────────────────────────────────────────────────┤
│ ② 首轮 User Prompt（prompts.build_review_request）            │
│    审查目标 / 目标类型 / 预扫描文件清单 / 用户关注点 / 交付要求 │
│    —— 注入本次任务的具体上下文                                │
├─────────────────────────────────────────────────────────────┤
│ ③ 动态提示（prompts.continuation_hint）                       │
│    按迭代阶段注入：未用工具 / 事实已建立 / 预算将尽 / 必须提交  │
│    —— Context Engineering：在正确的时机给正确的约束            │
└─────────────────────────────────────────────────────────────┘
```

---

## ① System Prompt 设计

### 结构：角色 → 目标 → 流程 → 纪律 → 工具 → 语言

**1. 角色（立人设）**

> 你是 CodeGuard，一名严谨、务实的高级代码审查工程师（Senior Code Reviewer），
> 服务对象是需要高质量评审意见的开发团队。**你拥有工具，可以主动查看代码库而不是凭空猜测。**

最后一句是关键：明确告诉模型"你有工具、应该用工具"，而不是把它当成一个
纯文本补全器。

**2. 工作流程（可执行的步骤，而非抽象要求）**

```
1. 先取客观事实：第一步总是调用 run_static_analysis …
2. 再读代码：对命中的重点位置用 read_file / search_code 阅读真实上下文 …
3. 补充语义层面问题：指出规则引擎无法发现的缺陷 …
4. 收敛并提交：信息足够后调用 submit_review 提交报告并结束。
```

用"总是""第一步"这类确定性措辞，比"建议先"有效得多。第 3 步还给出了
语义问题的**具体方向清单**（逻辑错误、边界条件、并发时序、异常策略、资源泄漏、
复杂度、接口契约、幂等性）—— 否则模型容易泛泛而谈。

**3. 审查纪律（抑制 LLM 审查的典型噪声）**

这是整个 Prompt 里最有价值的部分，每条都对应一类真实的失败模式：

| 纪律 | 针对的失败模式 |
| --- | --- |
| **禁止臆测**：每条问题必须能指向具体 `文件:行号` 并引用真实代码；无证据的怀疑写入 `open_questions` | 幻觉：编造不存在的代码和行号 |
| **禁止万能建议**：不要提交"补充类型注解""增加单元测试""加注释""遵循 PEP8" | 正确但无用的废话，稀释报告价值 |
| **必须判断而非罗列**：静态规则有误报，`subprocess.run([...])` 参数为字面量时是安全的，应主动排除 | 把工具输出原样当成结论 |
| **区分严重级别**：能导致安全事故/数据损坏/崩溃的 → critical/high；不要为了显得严谨而抬高级别 | 级别通胀，导致报告失去优先级意义 |
| **给出可执行修复**：suggestion 要具体到可以直接照做，尽量给出修正后的代码 | "建议优化一下"式空话 |
| **宁可少而准**：最多保留 15 条 findings，最有价值的排前面 | 报告过长，读者抓不住重点 |
| **正面反馈要具体**：写清"哪个文件/函数做了什么好的设计" | "代码结构清晰"这种零信息量夸奖 |

**4. 工具使用规范**

- 路径相对工作区根目录，先 `list_files` 了解结构
- **工具返回错误时根据错误信息调整参数重试，不要用相同参数重复调用** —— 这条
  显著减少了无效重试
- 不要为凑数反复调用工具，每次调用都要服务于一个明确的信息需求
- 调用 `submit_review` 后不再调用其他工具（显式终止语义）

**5. 输出语言**：简体中文，保留代码与技术名词原文，表达专业直接无客套话。

### 中英双语

`CODEGUARD_LANG=en` 时切换到英文版本，措辞与约束**一一对应**（不是简单翻译，
而是同等的约束强度）。

## ② 首轮 User Prompt

模板化的任务说明，包含：

| 段落 | 内容 | 作用 |
| --- | --- | --- |
| 审查目标 | 路径、目标类型（文件/目录） | 明确任务边界 |
| 预扫描文件清单 | 目录下探测到的源码文件（最多 40 条 + 总数） | **减少模型盲探成本**，省 token |
| 用户额外关注点 | `-f "SQL 注入" -f "并发安全"` | 让用户能引导审查重点 |
| 交付要求 | 逐条列出 `submit_review` 必须包含的字段 | 结构化输出，便于渲染 |

预扫描是一个务实的工程优化：不给清单的话，模型第一轮往往会先花 1~2 次
工具调用去"探索目录"，而这些信息在 Python 侧一行 `rglob` 就能拿到。

## ③ 动态提示（Context Engineering）

根据循环状态在**正确的时机**注入约束，而不是一开始就把所有限制堆进 System Prompt：

| 触发条件 | 注入内容 | 设计意图 |
| --- | --- | --- |
| 模型未用任何工具就想下结论 | "你还没有调用任何工具。请先调用 `run_static_analysis` 获取客观事实，不要仅凭想象下结论。" | 把跑偏的模型拉回事实轨道 |
| 第 1 轮结束 | "事实基础已建立。请继续阅读关键文件的真实上下文，剔除误报并补充规则引擎发现不了的语义问题。" | 明确告诉它"下一步该做什么" |
| 剩余轮数 ≤ 2 | "注意：迭代预算即将用尽。请立即基于已有信息调用 `submit_review`，未核实的内容写入 `open_questions`。" | **优雅降级**：预留收敛时间 |
| 剩余轮数 ≤ 1 或工具预算耗尽 | "工具调用次数已达上限。请**不要再调用其他工具**，立即调用 `submit_review` 提交当前结论。" | 强制收敛，避免报告难产 |
| 回复既无内容也无工具调用 | "请直接调用 `submit_review` 提交结论。" | 兜底空响应 |

**为什么不全部写进 System Prompt？** 因为约束的价值取决于时机。一开始就说
"预算将尽要赶紧收敛"会让模型过早放弃调查；而未用工具时讲"预算"则完全没有意义。

## Prompt 迭代记录

以下是开发过程中实际观察到的失效模式与对应的 Prompt 修正：

| 观察到的失败模式 | Prompt 修正 |
| --- | --- |
| 模型直接给出"整体看起来不错"的结论，未查看任何代码 | 流程第 1 步加"**总是**调用 `run_static_analysis`"；新增 `no_tool_used` 动态提示 |
| 报告里出现代码中不存在的行号与片段 | 纪律加"每条问题必须指向具体 `文件:行号` 并引用真实存在的代码片段" |
| 一半 findings 是"建议加类型注解/加测试" | 纪律加"禁止万能建议"并显式列出禁用措辞 |
| 把静态规则的误报原样抄进报告 | 纪律加"必须判断而非罗列"，并**举例说明**安全写法 |
| 所有问题都被标成 high | 纪律加级别定义与"不要为了显得严谨而抬高级别" |
| 工具报错后反复用相同参数重试 | 工具规范加"根据错误信息调整参数重试，不要重复相同调用" |
| 报告写到一半迭代次数用完，没有产出 | 新增 `nearly_out_of_budget` / `must_submit` 分段提示 |
| `positives` 全是"代码结构清晰" | 纪律加"具体到文件/函数，避免空泛夸奖" |

这些修正也体现在代码里：`prompts.py` 的每条提示、`agent.py` 的每个
`hint_kind` 触发条件，都能对应上表的一行。

## 可复用要点

如果要为其他任务（如文档生成、测试生成）设计 Agent Prompt，这套结构可以复用：

1. **角色 + 能力声明**：明确告诉模型它有工具、应该主动使用
2. **编号的可执行流程**：每步一个动作，用确定性措辞
3. **纪律清单**：只写"反失败模式"的约束，每条都对应一个真实观察到的坏行为
4. **逆向约束优于正向要求**："不要提交 X" 比 "请提交高质量的 Y" 有效得多
5. **动态提示按阶段注入**：把时效性约束从 System Prompt 里拿出来
6. **给方向而非给答案**：列出语义问题的检查方向，而不是让模型自由发挥
